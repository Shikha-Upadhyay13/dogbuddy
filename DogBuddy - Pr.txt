## 1. Product summary

DogBuddy is a staff-only web application for dog boarding facilities. It has three screens — **Login**, **Today's Dashboard**, and **DogBuddy Chat** — and one AI agent that can read data, update statuses, log incidents, and research dog health using live web search.

The prototype uses mock data populated by a seed script. The data must feel real.

## 2. Tech stack (locked)

Use exactly these. Do not substitute without approval.

### Backend
- **Language:** Python 3.11+
- **Framework:** FastAPI (latest)
- **Database:** SQLite via SQLAlchemy 2.0+
- **Auth:** JWT (via `python-jose`) + bcrypt (via `passlib`)
- **Agent framework:** `deepagents` (latest) + `langgraph` + `langchain`
- **LLM:** OpenAI `gpt-4o-mini` (via `langchain-openai`)
- **Web search:** Parallel AI Search API (via `httpx`)
- **Streaming:** Server-Sent Events (SSE) via `sse-starlette`
- **Env management:** `python-dotenv`

### Frontend
- **Framework:** Next.js 14 (App Router) + TypeScript
- **Styling:** Tailwind CSS 3+ (no shadcn for prototype — vanilla Tailwind)
- **State:** React `useState` and `useContext` (no Redux/Zustand for v1)
- **HTTP client:** Native `fetch`
- **Streaming:** Native `fetch` with `ReadableStream` reader
- **Icons:** `lucide-react`

### Tools
- **Package manager:** `pip` (backend), `npm` (frontend)
- **Formatter:** `black` (Python), `prettier` (TS)
- **Linter:** `ruff` (Python), `eslint` (TS)

## 6. Backend API specification

All endpoints return JSON. Errors use HTTP status codes + `{"detail": "message"}`.

All endpoints except `/auth/signup` and `/auth/login` require `Authorization: Bearer <JWT>`.

### Auth endpoints

#### `POST /auth/signup`
**Body:**
```json
{ "name": "string", "phone": "string", "password": "string" }
```
**Returns 201:**
```json
{ "token": "jwt_string", "staff": { "id": 1, "name": "...", "phone": "..." } }
```
**Errors:**
- 400 if phone already exists
- 422 if body validation fails

#### `POST /auth/login`
**Body:**
```json
{ "phone": "string", "password": "string" }
```
**Returns 200:**
```json
{ "token": "jwt_string", "staff": { "id": 1, "name": "...", "phone": "..." } }
```
**Errors:**
- 401 if invalid credentials

#### `GET /auth/me`
**Returns 200:**
```json
{ "id": 1, "name": "...", "phone": "..." }
```

### Dog endpoints

#### `GET /dogs`
Returns all dogs in the facility.
```json
[ { "id": 1, "name": "Rex", "breed": "...", ... }, ... ]
```

#### `GET /dogs/{id}`
Returns one dog with full details + current booking + recent incidents.

### Booking endpoints

#### `GET /bookings/today`
Returns bookings active today, grouped by status:
```json
{
  "checking_in": [ { "booking_id": 1, "dog": { ... }, "kennel_id": "K-01" }, ... ],
  "in_care":     [ ... ],
  "checking_out": [ ... ]
}
```

#### `PATCH /bookings/{id}/status`
**Body:**
```json
{ "status": "checked_in" | "in_care" | "checked_out" }
```
Returns updated booking. Writes an `audit_log` entry.

#### `PATCH /bookings/{id}/activity`
**Body:**
```json
{ "activity": "walk" | "feed" | "meds" }
```
Updates the corresponding `last_*_at` to now. Writes an `audit_log` entry.

### Incident endpoints

#### `POST /incidents`
**Body:**
```json
{
  "dog_id": 1,
  "type": "health" | "behavior" | "feeding" | "other",
  "severity": "mild" | "moderate" | "severe",
  "description": "string"
}
```
Returns the created incident. `staff_id` is taken from the JWT. Writes `audit_log`.

#### `GET /incidents/recent`
Returns the last 20 incidents across all dogs, most recent first.

### Chat endpoint

#### `POST /chat` (Server-Sent Events)
**Body:**
```json
{ "message": "string", "thread_id": "string" }
```
**Stream format:** SSE events
```
event: token
data: {"content": "Looking"}

event: tool_call
data: {"name": "query_db", "args": {...}}

event: tool_result
data: {"name": "query_db", "result_summary": "Found 4 dogs"}

event: token
data: {"content": " up Rex..."}

event: done
data: {}
```

`thread_id` is generated client-side per session and persists across messages so the agent has memory. Use the staff_id + date as the thread_id (e.g. `"staff_1_2026_05_26"`).

## 7. Agent specification

### Framework
Use `deepagents` (latest version, pinned in `requirements.txt`).

### Model
- **Primary:** OpenAI `gpt-4o-mini` (cost + speed balance)
- **Temperature:** 0.3 (slight warmth, mostly factual)

### System prompt
Stored at `backend/agent/prompts/main_system.md`. Loaded at agent init.

```markdown
You are DogBuddy — an AI copilot for dog boarding facility staff.

# Your role
You help staff manage 15–30 dogs at once. You are their senior colleague:
fast, accurate, never judgmental. You can update records, look up information,
log incidents, and research dog health topics on the live web.

# Hard rules (never break these)
1. SAFETY FIRST. For any question about medication, dosage, diagnosis, or
   treatment, always say "consult the facility vet." Never give doses.
   Never diagnose. Never recommend treatment.
2. CONFIRM before destructive actions. Before marking a dog as checked out
   or logging a severe incident, briefly confirm with the staff member.
3. NEVER make up facility data. If you don't know, query the database.
   If the database doesn't have it, say so.
4. ALWAYS cite sources when researching health topics on the web.

# How you work
- Use the right tool for the question:
  - Internal facility questions → query_db
  - Updating a booking → update_status
  - Logging an issue → log_incident
  - General health/breed/behavior research → web_search
- Reply naturally. Don't say "I'll call the tool now." Just do it.
- Keep responses short. Staff are busy.

# Today's context
Date: {today}
Staff on duty: {staff_name}
Facility: DogBuddy Boarding (single location prototype)

# Skills (read these before acting on relevant topics)
{medication_safety_skill}
{incident_logging_skill}
```

The `{...}` placeholders are filled at agent invocation time. The skill files are inlined here in v1 (not read on-demand).

### Skills

#### `backend/agent/skills/medication_safety.md`
```markdown
# Skill: Medication Safety

When a staff member asks about ANY of the following, follow this skill:
- Medication doses (any drug, any dog)
- Whether to give a medication
- Mixing medications
- Suspected poisoning or overdose
- Diagnosing a condition
- Treating a condition

## Required response pattern
1. Provide general, educational information ONLY (e.g. "chocolate contains
   theobromine which is toxic to dogs")
2. NEVER give a specific dose, even if asked directly
3. ALWAYS end with: "For dosing, diagnosis, or treatment, consult your facility vet immediately."
4. For suspected emergencies (poisoning, seizure, severe bleeding, choking),
   say "This sounds urgent — call your vet now" FIRST, then provide info.

## Forbidden phrases
- "Give X mg of Y"
- "The safe dose is..."
- "You can treat this with..."
- "It's probably just..."
- "Don't worry, it's normal"

## Always-include phrases
- "Consult the facility vet"
- "For diagnosis, talk to your vet"
- "I can share general information, but treatment decisions need a vet"
```

#### `backend/agent/skills/incident_logging.md`
```markdown
# Skill: Incident Logging

When a staff member reports something happened to a dog, log it as an incident.

## Severity guide
- **mild**: skipped meal, minor scuffle with no contact, mild limp, vomiting once
- **moderate**: physical altercation, refusing food >24h, persistent limping,
  diarrhea, unusual lethargy
- **severe**: injury with bleeding, seizure, suspected poisoning, dog attack,
  prolonged vomiting, unresponsive

## Required fields
- `dog_id`: which dog
- `type`: health / behavior / feeding / other
- `severity`: as above
- `description`: clear, factual, what happened (no opinions)

## Response pattern
1. Confirm the dog (look up by name → get id)
2. Confirm severity based on description
3. Log via the log_incident tool
4. Reply with: "✅ Logged for [dog name] — [type], [severity]. {next-action if needed}"
5. For severe incidents, add: "⚠️ This sounds serious. Notify the manager and consider calling the vet."
```

### Tools

Define four tools using LangChain's `@tool` decorator. Each must have a clear docstring (the agent reads these to decide when to use the tool).

#### Tool 1: `query_db`
```python
@tool
def query_db(query_type: str, params: dict = None) -> str:
    """
    Query the facility database. Use this for any question about dogs,
    bookings, owners, or incidents in the facility.

    query_type options:
    - "todays_bookings": all dogs in facility today (no params)
    - "dog_by_name": get dog details (params: {"name": "Rex"})
    - "pending_tasks": dogs needing walk/feed/meds (params: {"task": "walk"})
    - "recent_incidents": last 20 incidents (no params)
    - "vaccination_status": dogs with expiring/expired vaccines (no params)

    Returns: a human-readable summary string.
    """
```

#### Tool 2: `update_status`
```python
@tool
def update_status(dog_name: str, action: str) -> str:
    """
    Update a dog's status or activity.

    action options:
    - "check_in": mark dog as checked in
    - "in_care": mark dog as in care
    - "check_out": mark dog as checked out (REQUIRES CONFIRMATION)
    - "walked": record a walk now
    - "fed": record feeding now
    - "meds_given": record medication given now

    Returns: confirmation string.
    """
```

#### Tool 3: `log_incident`
```python
@tool
def log_incident(dog_name: str, incident_type: str, severity: str, description: str) -> str:
    """
    Log an incident for a dog.

    incident_type: "health" | "behavior" | "feeding" | "other"
    severity: "mild" | "moderate" | "severe"
    description: factual description of what happened

    Returns: confirmation string with incident id.
    """
```

#### Tool 4: `web_search`
```python
@tool
def web_search(query: str) -> str:
    """
    Search the live web for general dog health, breed, behavior,
    nutrition, training, or care information. Use this for questions
    that are NOT about the specific facility's data.

    DO NOT use this for medication dosing — always defer to the vet instead.

    Returns: synthesized answer with citation URLs.
    """
```

Implement `web_search` using Parallel AI Search API. Return a string with:
- A 3–5 sentence synthesis
- A "Sources:" section with up to 3 URLs

### Error handling

Every tool must be wrapped in `try/except` and return a sensible error string instead of raising. Example:
```python
try:
    result = ...
    return result
except Exception as e:
    return f"Could not complete that — {str(e)}. Try rephrasing or check the dashboard."
```

### Memory / threads

Use LangGraph's built-in checkpointer with SQLite backend. The `thread_id` is sent from the frontend (format: `staff_{staff_id}_{YYYY_MM_DD}`). This gives each staff member a daily memory that resets at midnight.

- Tool calls: show a small inline indicator "🔧 Updating Rex's status..."
- Tool results: render naturally inline (no separate bubble)
- Citations: render as small footnote-style links below the message

**Streaming:**
- New DogBuddy message starts as empty bubble with cursor blink
- Tokens append in real time as SSE events arrive
- "DogBuddy is thinking..." indicator before first token
- On `done` event, cursor stops

**Voice input:**
- Mic button → uses Web Speech API (`SpeechRecognition`)
- Tap mic → recording starts, button turns red, words appear in input

**Empty state (first time):**
Show 4 suggested prompt chips above the input:
- "Who's in today?"
- "What does Bruno eat?"
- "Mark Rex as checked in"
- "Symptoms of heatstroke in dogs?"

Tapping a chip fills the input — user still has to press send.

**Thread management:**
- Generate thread_id on first message: `staff_{staff_id}_{YYYY_MM_DD}`
- Send same thread_id with every message that day
- New day → new thread (handled client-side)

### Bottom Nav

Two icons + labels:
- 🏠 Dashboard
- 💬 Chat

Active state: cyan icon + text. Inactive: muted gray.

### Auth gating

- Root layout checks `localStorage` for token on mount
- If no token and path is not `/login` → redirect to `/login`
- If token and path is `/login` → redirect to `/dashboard`

### Logout

- Top bar of dashboard has a small "Logout" link

## 13. Known prototype limitations (acceptable)

These limitations are known and accepted for v1. Do not "fix" them unless instructed:

- SQLite locks under concurrent writes (~3 staff max simultaneously fine)
- No rate limiting on `/chat` (can burn OpenAI credits in dev — be mindful)
- JWT stored in localStorage (vulnerable to XSS — fine for prototype, change for prod)
- Web search has no caching (every research query hits Parallel API)
- Agent memory resets daily (intentional for prototype simplicity)
- No automated tests required for v1 (manual acceptance criteria above)
- No CI/CD pipeline required for v1
